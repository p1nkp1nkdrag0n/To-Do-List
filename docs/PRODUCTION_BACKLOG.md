## P01 重建排期 / 确认清单不是原子操作

**现象**

- 解析成功后先 `clearProjectSchedule()`，再逐条 `create_task`。
- 任一 `create_task` / `assign_member` / `set_dependency` 失败：
  - 旧排期已经被删；
  - 新排期只建了一半；
  - 接口仍可能返回 200 与 `finished`。
- 确认清单提交的是 `ownerName`：成员改名/退出后，`memberByName.get` 匹配不到，
  任务被 `continue` 跳过；旧排期已清空，最后 0 个任务、0 冲突。

**代码位置**

- `server/meeting/orchestrator.ts`：`beforeCreateTasks` 调用点、建任务循环。
- `server/meeting/meeting-router.ts`：`clearOnSuccess`。
- `RealtimeWorkspace.tsx`：确认清单的负责人下拉。

**修复设计**

1. 确认清单提交稳定 `userId`，不提交姓名。
2. 新增 MCP 工具 `replace_schedule(projectId, tasks[])`：
   - 一个短事务内完成：校验项目可写/未归档/成员有效 → 删除旧任务 → 插入任务/分工/依赖。
   - 任一步失败整体回滚，旧排期保留。
3. 编排器只调用一次批量入口，不再逐条写。
4. 删除前重验全部任务；存在失效项时整批拒绝，不发 `finished`。

**验收**

- 第一条创建失败、成功一条后第二条失败、分工失败、依赖失败：旧排期保留、HTTP 非 200、无完成事件。
- 成员改名/退出、owner 为空、部分 owner 失效：整批拒绝，旧排期保留。

**预估**：4–6 小时。

## P02 计划应用的快照补偿会覆盖并发修改

**现象**

`apply-plan.ts` 在失败时用整项目快照恢复：

- `DELETE ... WHERE id NOT IN (备份)` 会删掉另一连接刚建的任务/分工；
- `UPSERT` 会把人工改过的标题、revision 写回旧值。

“恢复函数自己包事务”不等于“整份计划原子提交”。

**代码位置**

- `server/mcp/apply-plan.ts`：`backupSchedule` / `restoreSchedule`。

**修复设计（分两步）**

1. **先做行级补偿（推荐先交付）**
   - 记录本次写入的行 id 与写入后 revision；
   - 失败时只回滚这些行，且仅当当前 revision 等于写入后 revision；
   - 不一致则保留并报告，不再整项目覆盖。
2. **再做完整事务（赛后）**
   - 抽出“事务内写入函数”，整份计划的校验与全部动作共享一个短事务；
   - 不把模型/网络/用户操作放进事务。

**验收**

- 双连接交错：A 应用计划中途失败，B 期间成功保存的修改必须保留。
- 先有一次成功写入再失败（仅把第一个动作改成不存在 ID 测不到问题）。

**预估**：行级 4 小时；完整事务 1–2 天。

## P03 撤销会覆盖后续人工编辑

**现象**

撤销时读“当前 revision”，再据此写回：

- 自动拆分 120 + 480 后，人工把原分工改成 30，撤销变成 510，并返回成功；
- 人工改负责人也会被覆盖。

**代码位置**

- `server/meeting/undo.ts`。
- `server/mcp/apply-plan.ts`：应用结果记录。

**修复设计**

1. 应用时记录每条记录写入后的 revision（before/after）。
2. 撤销前逐条校验：当前 revision 必须等于 after。
3. 不一致 → 拒绝本次撤销并提示“已被人工修改，未撤销”，保留用户修改。
4. 整次撤销的检查与写入放同一短事务。

**验收**

- 正常撤销、改工时后撤销、改负责人后撤销、拆出分工被改/删后撤销、重复撤销。

**预估**：4–6 小时。

## P04 方案指纹漏掉可用时间等排期输入

**现象**

`snapshotSignature` 只包含任务（id/start/due）与分工（id/user/start/end/minutes）。
没有可用时间档案、依赖、进度、revision。

结果：成员周容量从 600 降到 60，冲突数仍为 1，旧方案仍把 480 分钟派给他。

**代码位置**

- `server/mcp/reschedule.ts`：`snapshotSignature`。
- `server/mcp/apply-plan.ts`：应用前比较。

**修复设计**

- 指纹纳入：任务 revision、分工 progress/revision、可用时间档案（有效期/周容量/时段摘要）、依赖。
- 对拼接后的字符串做 sha256，降低长度。
- 任一输入变化 → 指纹变化 → 拒绝旧方案，要求重新试算。

**验收**

- 改容量、改依赖、改进度、改工时的旧方案均被拒绝；什么都没改则正常应用。

**预估**：2–4 小时。

## P07 初始化并发：本机免码 + 8 个并发请求都进入哈希

**现象**

- 本机免初始化码是桌面首启向导的设计选择；
- 并发请求都能通过 `needsBootstrap()` 预检查并进入 bcrypt 哈希；
- 事务内还有一次 `COUNT(*)` 检查，所以不会建出多个管理员，但存在 CPU 消耗窗口。

**代码位置**

- `server/modules/auth/auth-service.ts`：`bootstrapAdmin`。
- `server/modules/auth/auth-router.ts`。

**修复设计**

1. 进程内单飞（in-flight promise）或信号量，把首次初始化串行化。
2. 每 IP 频率限制。
3. 文档明确“本机免码”是设计选择，不宣称“初始化认证问题全部关闭”。

**验收**

- 8 个并发初始化：1 个 201，其余 409；只发生一次密码哈希。

**预估**：2 小时。

## L11 数据 / Key 存在程序目录，换版本可能被清空

**现象**

打包回退模式下数据在 `ToDoList-app\ToDoList-data`，与解压目录同级；
更新时若替换/删除解压目录，数据与用户 Key 可能一起丢失。

> 当前按使用者要求保留旧行为（便于反复测试时重填 Key）。分发前需要改回分离存储。

**修复设计**

1. 数据目录固定到 exe 同级 `ToDoList-data`，与解压目录分离。
2. 首次启动迁移旧目录数据。
3. 保留 `RESET_KEYS.txt` 作为测试开关。
4. 启动器与 C# 解压逻辑都要保留数据目录。

**验收**

- 删除 `ToDoList-app` 后重启，账号、项目、Key 仍在。
- 旧目录存在时自动迁移成功。

**预估**：2–3 小时。
